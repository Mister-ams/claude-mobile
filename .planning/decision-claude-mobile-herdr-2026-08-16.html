Claude Mobile (OTG) -- Improvement Review

2026-08-16 -- codebase audit (v3.2.18, HEAD d000058) + herdr research (v0.8.0) + iPad retarget. Five decisions, reliability-first sequencing, comment box per item. Security assessment appended separately.
Live status: the service is DOWN. No process in Windows or WSL PM2, nothing listening on :3456, zero /tmp/cm-*.dtach sockets. A reboot at some point since May took the whole stack down and nothing resurrects it; all sessions were lost with it. This is the exact failure class this review addresses: dtach gives no restore, PM2 was never wired to boot, and WSL shutdown erases the sockets. See D3 (do it regardless of direction).

1. The core finding

Roughly 520 of server.js's 2,033 LOC -- and its most fragile 520 -- exist only because dtach provides no structured API and no agent-state signal:

  • dtach/WSL layer, 308 LOC (~200 pure workaround): every query is a synchronous execSync wsl.exe bash -c shell-out; session discovery is ls /tmp/cm-*.dtach + regex; liveness is test -S; launch is a blind cmd.exe /c claude\r write after a hardcoded 500ms sleep; recovery attaches at hardcoded 80x24; reattach-by-respawn needs a generation counter to fence stale closures (server.js:42-157, 1225-1404).
  • Attention detection, ~107 LOC: 12 heuristic regexes over de-ANSI'd output -- including Claude Code's randomized spinner verbs ("Crunched/Cogitated for"), release-volatile by construction. Miss rate is high enough that ATTN-MISS logging is permanent instrumentation (server.js:912-983).
  • Out-of-band state, ~85 LOC: .session-meta.json for names/dirs dtach cannot store, plus the 400KB ring-buffer replay path that is dead in default grid mode.

herdr ships all of this as its core product, maintained upstream at weekly cadence: a daemon that owns PTYs, a JSON Socket API (pane.read/send_text, events.subscribe, session.snapshot), agent states idle / working / blocked / done with a maintained Claude Code manifest, and -- the step-change dtach can never offer -- restart restore including native Claude Code conversation resume by session identity. A reboot today loses everything; under herdr it restores workspaces, panes, cwd and re-attaches the Claude conversations.

What stays ours in every option: the Tailscale-serve topology, the auth stack (TOTP + WebAuthn + IP-bound tokens + rate limiting, ~479 LOC), E2E crypto (~342 LOC), the grid render pipeline (206 server + 309 client LOC), and the seven waves of iOS Safari polish -- keyboard, font metrics, swipe nav, viewport culling -- that no third-party frontend replicates.

2. herdr facts that gate the decision

  • github.com/herdrdev/herdr, v0.8.0 (2026-08-03), Apache-2.0 (relicensed from AGPL), ~30k stars, weekly stable releases, very active.
  • Socket API = newline-delimited JSON-RPC over a unix socket. No auth on the socket -- filesystem perms only. Acceptable here: our Node server is the only consumer and the phone-facing auth/E2E layer stays ours.
  • Claude Code state detection is also heuristic upstream (screen manifests, known lag, issue #1630) -- but it is maintained by 30k stars' worth of users instead of us, and a lifecycle-hook path exists for agents that integrate deeper.
  • Windows native = preview-only beta (no stable channel, no --remote, ConPTY quirks). The right home is WSL, where it is a well-trodden path with no exe-interop issues on the tracker.
  • Pre-1.0: protocol bumps can strand clients -- pin the binary version, upgrade deliberately.
  • Pane history is off by default (secret-safety); enable pane_history = true for scrollback replay.
  • Ecosystem proof the socket drives browser terminals: herdr-webui, herdr-gui, benkraus/herdr-mobile, and Collie (PWA + push notifications over Tailnet).

3. Decisions

D1 -- Direction

OptionWhat happensCost / risk
A Ops-only fix PM2 resurrect at boot + WSL keepalive + watchdog. No architecture change. ~0.5 day. Keeps all 520 LOC of scaffolding + heuristics; reboots still lose every session and conversation.
B -- RECOMMENDED herdr as the session backbone, keep our client herdr daemon in WSL owns the Claude PTYs. server.js drops the dtach layer, attention heuristics, meta persistence and recovery (-400 to -520 LOC) and instead consumes the Socket API (~+150 LOC): pane list/read/send_text for the terminal stream, events.subscribe for state -> push notifications on blocked/done. C Retire our client too; adopt Collie / herdr-webui claude-mobile becomes configuration. Zero owned code. Loses the iOS-tuned grid renderer, swipe nav, and our auth/E2E; third-party maturity unknown. Worth a 1-hour trial for calibration, not as the plan.
Recommendation: B, gated on spike S1. Optionally trial Collie for an hour first purely to calibrate whether C is closer than expected.

D2 -- How Claude runs inside herdr panes (only if D1 = B)

  • RECOMMENDED Native WSL claude: clean process tree, reliable herdr state detection, native session-resume identity. One-time claude login in WSL. Honest caveat: Windows-resident repos are reached via /mnt/c, which is slower for file-heavy work than today's Windows-native claude process -- mitigate by keeping active working copies (or worktrees) on the WSL ext4 side.
  • ALTERNATIVE Keep cmd.exe /c claude interop inside herdr panes: preserves Windows auth + NTFS speed, but the interop process tree likely defeats herdr's foreground-process agent detection and breaks resume identity. Test both in S1 before committing.

D3 -- Boot resilience (do regardless of D1)

  • Enable systemd in WSL; run the session backbone (herdr, or PM2 under option A) as a systemd unit.
  • Windows Scheduled Task at logon: start the WSL distro, re-assert tailscale serve, start the Node server.
  • Watchdog: the Node server already has a canary/audit layer; add a trivial self-check that the backbone socket answers ping.
~0.5 day. This alone would have prevented the outage found today. Recommendation: YES, first move.

D5 -- Retarget the client to iPad (operator request, 2026-08-16)

Not a skin change. The client is phone-shaped by construction, and three things are simply absent rather than merely tuned wrong:

GapEvidenceWork
No hardware-keyboard path at all -- the headline gap. All four keydown listeners are form-field scoped (index.html:47 rename, :446 TOTP, :450 activity tracker, :1987 message box). Every keystroke reaches the PTY only as a batched qsend(t + '\r') from a text box. index.html:1747-1862 Global key handler -> PTY: Esc, Ctrl-C/D/Z, arrows, Tab-completion, Cmd shortcuts. With a Magic Keyboard this is the difference between "usable terminal" and "SMS to a robot". Biggest single reliability/UX win on iPad.
No responsive layout -- style.css has zero width breakpoints; the only media query is prefers-reduced-motion (style.css:552). style.css Breakpoints at ~820/1180px. At iPad width the terminal is ~120-180 cols instead of ~50 -- Claude's TUI (diffs, tool output, tables) stops wrapping into mush.
Phone viewport -- maximum-scale=1.0, user-scalable=no. index.html:5 Reconsider zoom lock; keep interactive-widget=resizes-content for the on-screen-keyboard case, but hardware keyboard means it is often inert.
Swipe nav earns less -- 250 LOC of finger-following session switching that exists because a 390px screen shows one session at a time. iPadOS edge gestures also compete with it. index.html:1496-1745 On iPad: persistent tab bar, or (with herdr) a real multi-pane view. Keep swipe as a narrow-width behavior, do not make it the primary model.
T22 mouse tracking was skipped as "low value on touch-only mobile" (STATE-render-pipeline.yaml:86). iPad trackpad reverses that calculus. server.js:1149 (mouseTracking:false stub already in the Snapshot) Re-open T22 as a candidate -- the protocol field already exists.
Multi-client resize race gets worse -- last-writer-wins across clients (HANDOVER.md:24). iPad + iPhone both attached to one session will fight over PTY dims. server.js:1681-1707 Server-side arbitration (min-of-attached-viewers, or a designated primary) instead of purely client-side defensive re-assertion.

The hardware keyboard is what unlocks the screen -- operator's point, and it is the strongest argument for iPad. On iPhone the software keyboard eats roughly 40% of the viewport, which is why the font is tiny: it is the only way to see useful context in the remaining strip. An external keyboard means the on-screen keyboard never appears, so the terminal takes the full screen and can afford a substantially larger font. Two knock-on effects:

  • The bottom message box becomes optional rather than the primary input path -- freeing more vertical space still. Keep it as a compose box for long/multi-line prompts; direct keystrokes handle everything else.
  • All the interactive-widget=resizes-content machinery and the visualViewport keyboard handler (index.html:2086) go quiet on a hardware keyboard -- the single most bug-prone area of the client (7 waves of iOS keyboard fixes) simply stops being exercised. That is a reliability win, not just an ergonomics one.

Trade-off worth stating: a larger font means fewer columns -- perhaps ~100 rather than the ~180 a small font would give at 1366px. Still roughly double the iPhone's ~50, and readable beats dense. Make font size a setting so it can be tuned against column count in practice.

iPad strengthens the herdr case. herdr's workspace -> tab -> pane hierarchy is wasted on a 390px phone that can only render one pane. On an iPad it maps directly onto a real multi-pane layout -- watch two Claude sessions side by side, each with its own live agent state. The two changes compound; doing them together avoids building a phone-shaped session model twice.

Artifact handling -- nice-to-have (operator, 2026-08-16)

Explicitly a nice-to-have, not a reliability item -- but it is cheap on iPad and expensive on iPhone, so it belongs in the iPad track rather than as its own initiative. The house workflow produces HTML decision sheets, diffs, images, and PDFs constantly; today none of them are viewable from the phone. Sketch:

  • Detect files Claude writes in the session's project dir (or subscribe to a herdr plugin [[events]] hook) and surface a small "artifacts" tray per session.
  • Render inline: HTML in a sandboxed iframe (note: the R1 CSP tightening constrains this -- design it as a separate origin or a strict sandbox, not an inline injection), images natively, diffs in a simple viewer, PDFs via the native iPad viewer.
  • Prior art exists on the herdr socket: powerfooI/herdr-gui ships diff viewers, so this is a solved shape rather than a novel build.
Sequence: after the D5 keyboard + layout work and after D6 Tier 1 (the CSP change directly shapes how HTML artifacts can be rendered safely).

6. Security assessment (Opus 5 adversarial pass, verified first-hand)

Honest verdict: over-engineered on one axis, under-engineered on another, and the two barely intersect. The four layers are a well-built fortress facing the threat model of March 2026 -- when this was exposed via ngrok to the public internet (ngrokDomain in config.json at commit a28d6a6; audit log shows real public-internet IPs until 2026-03-19). You retired that exposure when you moved to tailscale serve. The code is a fossil of the old model. Two layers remain genuinely load-bearing; two defend a scenario so narrow they are a net negative -- and the surfaces a realistic 2026 attacker uses have none of the four pointed at them.

Broken crypto that no realistic adversary can currently reach

#Crypto sev / in-modelFinding
C1CRITICAL / Informational AES-GCM nonce reuse across directions. Both sides derive the SAME key (identical HKDF salt + info) and build the IV identically -- 4 zero bytes + BE64(counter), both starting at 1 -- with no direction bit in the IV, key, or AAD. Server message #1 is a 34-byte fixed known plaintext ({type:'encrypted',status:'ok'}); client message #1 is your TOTP. XOR the two ciphertexts and the TOTP code falls out in cleartext; seq 2 leaks the session token the same way; two tags under one nonce leak the GHASH subkey enabling forgery. Verified first-hand at server.js:336-337 and index.html:280-282. Textbook total break -- against precisely the attacker this layer exists to stop. Fix is one line: iv[0] = isServer ? 1 : 0.
C2HIGH / Informational Client downgrade: index.html:303 returns type:'encrypted' BEFORE the anti-downgrade guard at :341, and secureSend (:270-277) sends cleartext while e2eSendSeq === 0. An injected plaintext ack makes the client transmit its TOTP in the clear. Server-side anti-downgrade is correct by contrast.
C3-C6MED-INFO Client permits post-handshake rekey (server correctly refuses); signature covers only the ephemeral pubkey (no salt/transcript/freshness); TOFU first-contact and key-change warnings are both one confirm() tap. derToP1363 only ever parses the server's own signature -- unreachable, leave it.
A2MED (latent) getClientIP (server.js:1416) takes the leftmost XFF hop -- the most attacker-controllable position, and the opposite of what proxy-addr does two functions away. Currently rescued by Tailscale stripping inbound XFF. Worst case is rate-limit evasion and audit-log forgery, not a setup bypass.
N1LOW today / CRITICAL after any config edit wslExec (server.js:82) interpolates into bash -c "..." escaping only double-quotes, through cmd.exe which does not honour \". No client-reachable path today (dirs are allowlisted by exact match; session ids are numeric Map keys). The day a project dir contains a backtick, $, or &, it is root RCE in WSL. Convert to execFileSync with an argv array.

Explicit non-issues (checked, they are fine)

  • The localhost gate is NOT spoofable. The bypass you would most worry about -- X-Forwarded-For: 127.0.0.1 through tailscale serve to reach /setup or TOTP reset -- does not work. Express trust proxy: 'loopback' delegates to proxy-addr, which walks from the socket end and returns the first UNTRUSTED hop, so the appended real tailnet IP always wins. Empirically confirmed: every upload since 2026-03-19 logs ip=100.101.101.111.
  • Command injection via msg.session -- unreachable (numeric Map keys; a crafted string cannot both satisfy sessions.get() and reach the shell).
  • Upload path traversal -- none; the filename is server-generated.
  • Secrets in git history -- none. .totp-secret, .server-identity-key, .credentials.json were never committed.
  • Timing-safe comparison -- not applicable (Map lookup) / handled by otpauth.
  • Known-CVE dependencies -- none. express 4.22.1, ws 8.19.0, node-pty 1.1.0 all post-fix. @simplewebauthn/server v10 is 3 majors behind but has no known CVE.
The most likely way this box actually gets owned: not any attack above -- a poisoned npm patch release. 121 transitive packages, npm install --production (not npm ci, so the lockfile is advisory), no audit gate in CI (which only runs node --check), on a process that shells into WSL as root and holds ANTHROPIC_API_KEY. npm ci + npm audit --audit-level=high in CI is worth more than the entire E2E layer.

D6 -- Security fix batch

Tier 1 -- do now (~half a day, mostly one-liners):

  • R1: allowlist https:/http:/mailto: on the OSC-8 href; everything else renders as a plain span. Then tighten CSP -- drop 'unsafe-inline' from script-src (move inline JS to a file; CI already parses it separately) and narrow connect-src to 'self'.   • Supply chain: npm ci in install.sh/update.sh; add npm audit --audit-level=high to CI.

Tier 2 -- same week: Origin check on the WSS upgrade (R2) and on /api/totp/reset (R3); delete the req.query?.st token source; sanitize msg.name at create; getClientIP -> rightmost hop; wslExec -> execFileSync argv.

Tier 3 -- the E2E decision (your call):

  • RECOMMENDED Fix it (~10 lines) and stop calling it a security boundary. Direction byte in the IV; move the encrypted / key-exchange checks below the anti-downgrade guard; client refuses plaintext once a handshake begins. Keeps the rogue-control-plane defence honest.
  • Or delete it -- recover 342 LOC and a class of decrypt-failure reconnect bugs, lose only the rogue-Tailscale-control-plane case. Assessor's note: would fix rather than delete, but would not build it again from scratch today.
  • Either way: do not leave it as-is. As-is it is the one thing making these two layers a net negative.
