Delivery plan · claude-mobile 4.0.0

Windows-native: herdr replaces dtach, WSL leaves the path

Everything already runs on Windows except session persistence. Move that last piece and the architecture collapses to one operating system, no boundary crossings, and no migration of anything.

Target state

TODAY iPad -> tailscale -> [Win] node -> wsl.exe -> dtach -> bash -> cmd.exe /c claude -> [Win] Claude two boundary crossings, WSL on the critical path TARGET iPad -> tailscale -> [Win] node -> herdr (ConPTY panes) -> claude -> NTFS repos one OS, no crossings, nothing moved

What makes this cheap

Claude Code is already on Windows and already authenticated. The repos are already on NTFS, where find + stat over 2,016 files takes 119ms. Tailscale is already on Windows. The only thing living in WSL is dtach — and herdr v0.8.2 hosts native ConPTY panes on Windows, which is precisely dtach's job.

WSL is not removed from the machine. It keeps running the 11 Actions runners. It just leaves claude-mobile's critical path.

Risks

1. herdr stability is the real risk, and P0 does not retire it

45 crash-shaped lines and repeated SIGABRT on Linux on 17 August — the same day it was installed and tried. Windows is a different build, so the number transfers nothing in either direction. Only P2's soak answers this, and it takes a week, not an hour.

dtach is the incumbent it must displace: 236 server restarts across five months, zero aborts. That is a high bar for a pre-1.0 tool, and it is the bar that matters — this thing holds your working sessions.

2. Pre-1.0 protocol churn

v0.8.0 to v0.8.2 already changed what platforms ship. Agent state also lives in a remotely-fetched manifest outside the version pin — which is how a busy Claude got reported idle for 367 samples. The Windows integration hook should make detection authoritative and bypass the manifest entirely, but P0.3 must confirm that rather than assume it.

3. We are replacing the one component that has never failed

Everything else in this system has broken at some point. dtach has not. The upside is real — agent state, resume, ~800 lines deleted — but the thing being swapped out is the quiet, reliable part. That is why dtach stays behind a flag through P3 and is not deleted until a week of evidence says so.

4. Windows-specific unknowns

Cursor flicker is documented. SmartScreen may object to an unsigned binary. ConPTY behaviour under a server-side @xterm/headless mirror is untested by anyone, since that combination is unusual. None of these are likely to be fatal; all of them are P0 findings rather than assumptions.
