Two things to accept before you start, rather than discover on day three

No scrollback above the viewport. herdr panes are alt-screen, so the grid snapshot carries the viewport and nothing above it. Scrolling back on the iPad gets you nothing. This is structural to herdr rather than something we left unfinished, and it is a real regression against dtach.

Every restart signs you out. Tokens live in an in-memory Map (server.js:377), and the 8-hour idle auto-shutdown means a TOTP re-auth roughly daily. Whether to persist tokens across restarts is a security-posture decision, not an oversight.

Incident, 29 August — a junction turned a cleanup into a deletion

Tearing down the build worktrees, Remove-Item -Recurse -Force followed a node_modules junction into the live checkout and deleted through it. 115 entries went to 48 and node-pty stopped loading — while /health on both instances kept answering ok with live sessions, because a running process holds its modules in memory.

This is the same signature as the 24 August npm ci incident, from a different direction: invisible in operation, and it would have surfaced only when the 8-hour idle shutdown next restarted 3456 — overnight, with nobody watching. Repaired by the documented procedure (stop, npm ci, verify node-pty loads, start); 3456 came back with Recovered: "LOOMI OS" (cm-0), the same session. 3457 was never affected — it has its own node_modules.

The lesson is narrow and worth keeping: a junction is not a copy, and a recursive delete does not know that. Unlink it first — rmdir, or Directory.Delete(path, false) — and only then remove the directory. Better still, do not junction into a live tree at all; give the throwaway its own install.

Standing risks

herdr stability — not retired by P0

45 crash-shaped lines and repeated SIGABRT on Linux, 17 August. Windows is a different build so the number transfers nothing either way. Only P2 answers this, and it takes a week. We are replacing the one component in this system that has never failed.

The six days since 23 August bought nothing against this risk. The herdr instance sat idle and unreachable, so its clean log is evidence of disuse, not of stability. The clock on the week has not started.

What P1 changed about the risk picture

Restart survival is proven on herdr, which was the open question that mattered most — but it needed a fix we did not know we needed, and the failure was silent: the session was simply gone after a restart, with nothing logged as wrong. Two more of the same shape turned up in the same work: a sizing guard that could never fire because the client sends rows=200, and a column check that estimated a number herdr api snapshot reports exactly.

The lesson to carry into P2: this system fails by reporting success. Green CI, a returned ok:true, and a written state file all agreed while the update had actually failed. Watch the soak for outcomes, not for absence of errors.

Reversibility, at a glance

P0 undoes by deleting a folder. P1 ships with the flag defaulting to dtach, so nothing changes until P3.1 flips it. P3.1 undoes by deleting one line from 3456's config.json and restarting — and the dtach session survives in WSL throughout, so flipping back restores the running session rather than starting a fresh one. P3.2 and P3.3 are the real point of no easy return — deliberately placed after a week of evidence.
