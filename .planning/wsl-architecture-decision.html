WSL-only versus half-WSL

They are not competing designs. Half-WSL is a prefix of WSL-only — the same first move, stopped one step early. The question is what stopping buys, and whether it is worth what stopping costs.

Superseded — read this first (22 August)

This document recommended WSL-only on the strength of one unique benefit: that only a Claude running inside WSL could be seen by herdr. That is no longer true. herdr v0.8.2 ships herdr-windows-x86_64.zip; the server runs natively on Windows with ConPTY panes, agent process-tree detection, Claude Code integration install, and session persistence after the client detaches. Their docs say WSL is "neither required nor recommended".

The original NO-GO — and this document — rested partly on "v0.8.0 ships no Windows binary." When a decision rests on a version-pinned fact, it expires with the version. A fourth option is added below and the recommendation is revised. The filesystem measurements are unaffected and still correct; what changed is which way they point.

What the fourth column costs: nothing that has to move

No repo cloning, no memory-slug remap, no Claude re-authentication, no second distro, no CI coupling. It also deletes more code than WSL-only does — the wsl.exe scaffolding, the cmd.exe /c claude interop launch, and the dtach layer all go. WSL leaves the critical path, which incidentally disposes of the /tmp-purge problem and the sleep/resume networking fragility the readiness audit found.

The open question that decides it

herdr terminal attach is explicitly unsupported on Windows, and that may be exactly the mechanism the server needs — today node-pty spawns wsl.exe ... dtach -a to get a PTY onto a session. The docs do say Windows Terminal and PowerShell can attach to existing sessions, so the client path works; what is unproven is whether our server can drive a pane programmatically.

Two further unknowns: documented cursor rendering that "may flicker, jump, or briefly remain at an old position" on Windows, which matters for a terminal UI; and stability — the 45 crash-shaped log lines we found were on Linux, so Windows is simply untested.

Read the middle column carefully

Half-WSL keeps cmd.exe /c claude — the interop launch, its two shell layers, and the --exec subtlety that already cost one bug to get right. WSL-only deletes that line entirely. The more ambitious option is the smaller diff.

Read the last row before anything else

Windows-native wins or ties on every line except one, and that one is not a trade-off — it is an unknown. Both WSL options rest on dtach, which has held sessions through 236 server restarts across five months. Windows-native rests on a mechanism nobody here has exercised. That asymmetry is why the recommendation is "test it", not "do it".

3. What each uniquely buys

Half-WSL buys exactly one thing

Windows-native repo access. That is the entire differentiator. Every other row on its side of the ledger, WSL-only matches or beats.

WSL-only bought the herdr unlock — and no longer does

herdr's Claude integration is a hook that only ever fires for a Claude running in WSL, and no half-measure reaches it.

True of v0.8.0, false of v0.8.2. herdr's Windows build installs Claude Code integration on Windows and does agent process-tree detection there. Removing this row removes the entire case for WSL-only — it was the one thing the migration bought that nothing cheaper could.

And the filesystem argument now points the other way

The 373x measurement answered a conditional: if Claude moves to Linux, must the repos follow? Yes. It never argued Claude should move — the herdr unlock did. With that gone, the same data argues for staying: the repos are already on NTFS, which is already native to where Claude already runs. Moving them would introduce a penalty that does not currently exist.

The honest asymmetry

The WSL options are backed by measurements. Windows-native is backed by a documentation page and a release asset listing. It looks better on every axis precisely because nothing has been tried yet — and the third row above is the one that would take weeks, not an hour, to retire.

The asymmetry is the whole finding

Folklore says the WSL filesystem boundary costs 5-20x. Measured here it is 373x one way and 7.5x the other. Two facts follow. First, the current architecture is right to keep Claude on Windows while repos are on NTFS — that double crossing is buying something real. Second, once repos move to ext4 the calculus inverts completely, and the same reasoning that justifies today's design argues for going all the way.

6. Recommendation

Revised 22 August: test Windows-native first. Do not start the WSL migration.

The fourth column reaches every goal the migration was for — zero crossings, native filesystem, herdr able to see the agent — while moving nothing, re-authenticating nothing, and keeping WSL out of the path that gates your production deploys. It deletes more code than WSL-only does.

It hinges on one unproven mechanism: whether the server can get a PTY onto a herdr pane on Windows when herdr terminal attach is unsupported there. That is roughly an hour to answer, non-destructively, alongside the running service. If it works, the entire WSL programme is unnecessary. If it does not, we return here having lost an hour.

The previous recommendation stands only as a fallback, and if we do end up in WSL it should be a dedicated distro rather than Ubuntu-24.04 — that distro hosts 11 Actions runners serving the required checks on three repos, so putting an unstable experiment beside it puts your merges and deploys behind it.
